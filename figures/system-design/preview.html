Containment harness: system design figures

Design drawings for the planned harness and evaluation framework. No measured result is plotted.

Figure 1  Previously, keeping agents inside their authorization boundary took a hand-written guardrail for each application. The harness takes plain task requests and guides one unmodified agent with a scope contract compiled from each request.

(a)  Example input to the harness: a task with its stated scope and an unmodified agent loop.

(b)  The plain agent meets a blocked route and may finish through a reachable resource that was never granted, instead of stopping with an honest blocker report.

(c)  The harness compiles the request into a scope contract and plans over the granted actions (Grant Look-ahead). The agent then acts through a gateway that records every committed effect (Effect Journal) and returns it with fresh advice. Advice is not enforcement.

Figure 2  Agent workflows. (a) shows an example input. (b) shows the plain agent on that input. (c) shows the harness workflow around the same agent.

Figure 3  Evaluation framework. Incident records become task families in a frozen plan. One control layer runs any agent against simulated backends today and real tool backends later. Outcomes are read from replayed service effects, not from the agent's own account.

Figure 4  Integration with Inspect. Each harness component (green) implements one Inspect extension point (blue). An approver can only approve, modify, reject or escalate a call, so advice and journal text reach the agent between turns. The scorer reads the effect record from the sandbox.

Figure 5  A CRUX-style open-world evaluation run through the harness. The same contract and gateway are exercised first on simulated backends and then on real services. Each CRUX recommendation draws on one harness artifact.
