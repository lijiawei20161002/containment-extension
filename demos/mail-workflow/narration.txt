Containment-extension: an email workflow

Executed local fixture. Scripted actor. Declared scope. No live email sent.


01. An agent, an inbox, and a boundary.

What happens when an AI assistant handles your email? Let's follow one concrete workflow, and see where the containment extension fits.
This animation replays existing code against a local mail fixture. The actor is scripted, and no live email is sent.

02. Inspect runs evaluations. CRUX studies real work.

Inspect is an open-source framework for evaluating AI systems. It organizes tasks, agents, tools, logs, and scoring.
CRUX is a research project for open-world evaluations: longer, realistic tasks, with close observation and documented human interventions.
CRUX is not a plugin loader. Inspect is the software framework; CRUX describes how researchers investigate performance in real work.

03. A customer is waiting for a reply.

A customer reports a delivery delay. The user asks the assistant to request the missing diagnostics by replying to that email.
The instruction also says: do not update the internal ticket. Reading related information does not authorize every possible follow-up action.

04. Turn the request into an explicit boundary.

For this demonstration, we declare the scope directly from the user's instruction, then run the existing contract compiler.
Grant Look-ahead recommends replying to message zero one. The ticket write is outside that scope. This is advice; the actor still chooses its actions.

05. Read. Compose. Reply.

The scripted assistant fetches the message, drafts a request for diagnostics, and calls email reply.
The local service records one reply to the original sender. The internal ticket remains unchanged. No real inbox is contacted.

06. Record the effect that actually happened.

The Effect Journal records the committed reply and marks it within the declared scope. The planner now recommends finishing.
This fixture checks the operation and its target. It does not judge the free-form email body or prove real-world delivery.

07. What if the agent also updates the ticket?

Now replay an alternate branch. After the authorized reply, the scripted actor ignores the finish advice and adds a ticket comment.
The current tool runtime executes it. The journal flags the committed write as outside scope, but cannot undo it.
Blocking a write before execution requires a separate approval or enforcement layer. A journal alone is not that layer.

08. “Follow up” leaves a decision unresolved.

If the user only says, follow up, the channel is unclear. In this branch, our declared contract requires clarification.
The existing planner returns ask user: email the customer, or comment on the ticket? The scripted actor makes no writes while that choice remains unresolved.

09. Build on Inspect’s native components.

Begin with a dataset: one email request and workspace per sample. An Inspect task combines setup, an agent, tools, and scorers.
Inspect's model layer selects the provider and generation settings. The built-in ReAct agent can run the tool loop.
Our extension adds the scope contract, planner advice, and effect feedback inside that existing structure.

10. One email action through Inspect’s native loop.

Before the first model turn, a setup solver would provide scope and initial advice. A continuation callback can supply updated planner and journal feedback between turns.
Email actions would use Inspect custom tools, or locally executed MCP tools. A separate approval policy can approve, reject, or escalate before execution.
The tool backend must still record the effects it actually commits. An approval decision alone is not proof of what happened.

11. Run comparisons. Open the evidence.

Inspect eval sets can organize the same tasks across models and feedback conditions, with concurrency and execution limits.
We would explicitly configure retries and stopping rules, retain incomplete outcomes, and keep every trial's workspace isolated.
Inspect View, data frames, and transcript scanners support analysis. Our scorers would report unauthorized effects and authorized completion from the service record.

12. Package the adapter as an Inspect extension.

Inspect supports packaged tasks, solvers, tools, scorers, approvers, and monitoring hooks through its extension system.
That can make setup convenient once the adapter exists. Installing a package alone does not connect arbitrary mail systems or add containment to every task.
Other features follow the task: multimodal input for attachments, multiple agents for separate roles, or a sandbox for untrusted code.

13. CRUX would use it as an experimental intervention.

For a CRUX-style study, researchers could compare agents with and without this feedback during longer tasks.
They would retain the action trace, actual effects, user clarifications, and human interventions, then review where the advice changed behavior.

14. Can I load it with one click? Not yet.

The planner, journal, and local office fixture already run. This video executes those components.
The repository has a legacy ImpossibleBench-specific Inspect adapter, but no general one-click Inspect or CRUX integration.
The next step is a tested Inspect adapter with real tool bindings, effect collection, and any required approval policy.
